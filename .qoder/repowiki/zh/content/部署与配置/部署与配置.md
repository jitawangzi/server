## Maven多模块构建流程

### 构建命令

Maven多模块项目的标准构建流程如下：

```bash
# 清理所有模块的构建输出
mvn clean

# 编译所有模块
mvn compile

# 运行所有模块的单元测试
mvn test

# 打包所有模块（生成JAR文件）
mvn package

# 安装到本地Maven仓库
mvn install

# 部署到远程仓库
mvn deploy
```

### 构建生命周期

项目构建遵循Maven标准生命周期：

1. **validate**: 验证项目是否正确且所有必要信息可用
2. **compile**: 编译源代码
3. **test**: 使用合适的单元测试框架运行测试
4. **package**: 将编译后的代码打包成可分发格式（JAR）
5. **verify**: 对集成测试的结果进行检查
6. **install**: 将包安装到本地仓库
7. **deploy**: 将最终包复制到远程仓库

### 模块依赖关系

各模块之间的依赖关系通过`pom.xml`文件中的`<dependencies>`元素定义。父POM通过`<dependencyManagement>`统一管理所有依赖的版本号，确保版本一致性。

## 部署包结构与资源包含规则

### package.xml配置解析

`package.xml`文件定义了Maven Assembly插件的打包规则，用于生成最终的部署包。

```xml
<assembly xmlns="http://maven.apache.org/ASSEMBLY/2.1.0"
    xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
    xsi:schemaLocation="http://maven.apache.org/ASSEMBLY/2.1.0 http://maven.apache.org/xsd/assembly-2.1.0.xsd">
    <id>aof</id> 
    <formats>
        <format>zip</format>
    </formats>
    <dependencySets>
        <dependencySet>
            <outputDirectory>/lib</outputDirectory> 
            <useProjectArtifact>false</useProjectArtifact>
            <scope>runtime</scope>
            <includes>
                <include>cn.game:util</include>
                <include>cn.game:protocol</include>
                <include>cn.game:core</include>
            </includes>
        </dependencySet>
    </dependencySets>
    <includeBaseDirectory>false</includeBaseDirectory>
    <fileSets>
        <fileSet>
            <outputDirectory>./</outputDirectory>
            <directory>target/classes</directory>
            <excludes>
                <exclude>log4j2.xml</exclude>
            </excludes>
        </fileSet>
    </fileSets>
</assembly>
```

### 部署包结构规则

1. **输出格式**: ZIP格式压缩包
2. **依赖管理**:
   - 所有运行时依赖（runtime scope）被打包到`/lib`目录
   - 显式包含`util`、`protocol`、`core`模块的JAR文件
   - 不包含项目自身的artifact（`useProjectArtifact=false`）
3. **类文件**: 编译后的class文件直接放置在根目录
4. **基础目录**: 不生成与包名相同的根目录（`includeBaseDirectory=false`）
5. **排除文件**: 排除`log4j2.xml`配置文件

### 打包流程

当执行`mvn package`命令时，Maven Assembly插件会：
1. 编译当前模块
2. 收集指定的依赖JAR文件到`lib`目录
3. 复制编译后的class文件
4. 生成ZIP格式的部署包

## 服务器启动脚本使用方法

### game.sh脚本功能

`game.sh`是Linux/Unix系统下的服务器启动脚本，提供以下功能：

```bash
# 支持的命令
start    # 启动服务器
stop     # 停止服务器  
restart  # 重启服务器
status   # 查看服务器状态
help     # 显示帮助信息
```

### 使用方法

```bash
# 启动游戏服务器
./game.sh start

# 停止游戏服务器
./game.sh stop

# 重启游戏服务器
./game.sh restart

# 查看服务器状态
./game.sh status
```

### 脚本工作机制

1. **进程管理**: 使用PID文件（GameServer.server）跟踪服务器进程
2. **日志重定向**: 输出日志到`logs/out.log`文件
3. **后台运行**: 使用`nohup`命令确保进程在终端关闭后继续运行

### 关键配置参数

- **ServerName**: 服务器名称标识
- **JAVA_HOME**: Java安装路径（需根据实际环境配置）
- **MAIN_CLASS**: 主启动类`cn.game.games.net.game.GameServer`
- **APP_ARGS**: 应用程序参数`hc_game_1`

## JVM参数调优建议

### 当前JVM参数分析

`game.sh`脚本中配置的JVM参数如下：

```bash
JVM_ARGS="-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=oom.dump
-Xmx4g
-Xms256m
-Xss256k
-XX:MaxDirectMemorySize=256m
-XX:+UseG1GC 
-XX:+UseCompressedOops 
-XX:+UseCompressedClassPointers
-XX:+SegmentedCodeCache 
-verbose:gc
-XX:+PrintCommandLineFlags
-XX:+ExplicitGCInvokesConcurrent
-Djava.security.egd=file:/dev/./urandom
-Xlog:gc*,safepoint:logs/gc.log:time,uptime:filecount=100,filesize=50M
--add-opens java.base/java.lang=ALL-UNNAMED
--add-opens java.base/java.util=ALL-UNNAMED -Dio.netty.tryReflectionSetAccessible=true"
```

### 参数详解

#### 内存配置
- **-Xmx4g**: 最大堆内存4GB
- **-Xms256m**: 初始堆内存256MB
- **-XX:MaxDirectMemorySize=256m**: 直接内存最大256MB
- **-Xss256k**: 线程栈大小256KB

#### 垃圾回收配置
- **-XX:+UseG1GC**: 使用G1垃圾收集器
- **-XX:+HeapDumpOnOutOfMemoryError**: OOM时生成堆转储
- **-XX:HeapDumpPath=oom.dump**: 堆转储文件路径
- **-Xlog:gc***: 详细的GC日志记录

#### 性能优化
- **-XX:+UseCompressedOops**: 使用压缩普通对象指针
- **-XX:+UseCompressedClassPointers**: 使用压缩类指针
- **-XX:+SegmentedCodeCache**: 分段代码缓存

#### 安全与调试
- **-Djava.security.egd=file:/dev/./urandom**: 加快SecureRandom初始化
- **--add-opens**: 开放Java模块系统访问权限

### 调优建议

1. **生产环境调整**:
   - 将`-Xms`设置为与`-Xmx`相同值，避免堆动态扩展
   - 根据实际内存情况调整堆大小

2. **监控建议**:
   - 定期检查GC日志`logs/gc.log`
   - 监控OOM dump文件以分析内存泄漏

3. **性能优化**:
   - 根据实际负载调整G1GC参数
   - 考虑使用JVM profiling工具进行深入分析

## 高级部署策略

1. **环境准备**: 维护两套独立的服务器环境（蓝色和绿色）

   - 将新版本部署到非生产环境（如蓝色环境）
